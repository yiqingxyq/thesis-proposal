

\part{Analyses and Principles: What Makes Coding Agent Training Effective?}
\label{part:generalizability}

\start{Overview of Part~\ref{part:generalizability}}
% In Part I, we assume that training on the same tasks for evaluation, and we assume that using successful trajectories always work! 
\autoref{part:scalability} focuses on constructing training environments for coding agents that are both scalable and effective.
It makes two assumptions about training effectiveness: (1) a single training task is sufficient, and (2) task success alone is sufficient for selecting training demonstrations.
However, these assumptions do not always hold.
Our further analyses show that (1) training on a single task is insufficient for generalization to diverse downstream tasks, and (2) even successful demonstrations can differ substantially in their training effectiveness.

In this part, to make more accurate assumptions on coding agent training, we take a step back and \textbf{study the factors that make coding agent training effective}.
Both chapters follow the same structure: we first investigate the abilities that coding agents need to learn, then derive principles for designing training data that develops these abilities.

\start{Chapter \ref{chap:hybrid-gym}}
In \autoref{chap:hybrid-gym}, after analyzing and comparing multiple real-world coding agent tasks, we find that there are several common problem-solving stages that are shared across tasks, such as repository exploration and solution implementation.
As a result, we aim to improve coding agents' ability to perform each stage correctly and derive a set of principles for designing effective synthetic training tasks towards this goal. 
For instance, tasks must require non-trivial planning and repository exploration, as well as a code patch as the output of the solution implementation stage.
Guided by these principles, we build our dataset, \textbf{\hybridmethodname}, using a set of scalable synthetic tasks, such as function localization and dependency search.
Experiments show that agents trained on our synthetic tasks generalize effectively to diverse real-world tasks (e.g., issue-solving, test generation, and library construction) that are absent from the training data.

\start{Chapter \ref{chap:effective-analysis}}
The task design principles derived in \autoref{chap:hybrid-gym} require training demonstrations to include problem-solving stages such as repository exploration and solution implementation. We further observe that it is not sufficient to design reasonable training tasks. The training effectiveness also depends substantially on \textbf{how} these stages are carried out.
For instance, two sets of training demonstrations may both successfully locate target files in a codebase, yet the strategies they use can lead to substantially different performance after training.

\autoref{chap:effective-analysis} thus investigates which fine-grained behaviors agents should learn to improve their performance. 
Here we define a ``behavior'' as a pattern in how an agent carries out a problem-solving stage, including its strategies, tool choices, tool-call commands, and patterns ofreasoning text.
To efficiently identify behaviors that could potentially affect training effectiveness, we present \toolName, an analysis method that automatically discovers candidate behaviors by defining, extracting, and comparing the behaviors of different trained agents.
\toolName identifies behaviors that influence training effectiveness for at least one model, including specific repository exploration strategies, planning and verification patterns, and the verbosity of reasoning text.

The insights from \toolName can improve the effectiveness of training data generated for the \hybridmethodname synthetic tasks through various practical methods, including data selection, agent step synthesis, and behavior-conditioned rollout.
For instance, when training on the \hybridmethodname function localization task, inserting LLM-synthesized explicit planning steps into the training demonstrations improves Qwen3-8B's resolved rate on SWE-Bench Verified from 11.6\% to 17.6\%.

\section{Introduction}

% [Para-1: an overview of coding agent and its training]
Recent advances in large language models have enabled LM-based agents~\citep{sweagent,openhands} to tackle real-world coding tasks, with rapid progress in benchmarks such as the SWE-Bench issue resolution benchmark~\citep{swebench}.
While most existing methods only focus on the issue-solving task~\citep{swegym,R2EGym,swe-smith}, the application of coding agents can be diverse in real-world usage. A recent study show that more than 70\% of the real-world prompts target other software engineering tasks~\citep{valerie-interaction}.

% [Para-2: motivate task transfer]
As shown in a concurrent work~\citep{swe-play}, training on a single task can lead to overfitting and is not sufficient for generalizing to general coding agent tasks.
In particular, agents trained on issue solving do not transfer reliably to tasks such as test generation or library implementation. This calls for training coding agents with stronger \textbf{task generalization} capabilities.
Yet, in the current literature, task transferability for coding agents remains underexplored. 
In this work, we ask: what commonalities do real-world coding tasks share? How can we design training tasks that transfer effectively across a broad range of coding agent tasks?

% [Para-4: our analysis results]
To answer these questions, we start by decomposing real-world tasks into intermediate components (e.g., reasoning and repo-exploration) and analyzing the model's capabilities on each.
These results are shown in \autoref{fig:intro}.
We observe that a large number of actions in successful trajectories are spent on reasoning, repo-exploration, and implementation.
These categories also remain challenging for current coding agents.
For instance, even after finetuning on issue-solving~\cite{swegym}, the agent still has file editing failures for the majority of the examples.

Fortunately, these intermediate components can be isolated from the construction of coding environments with executable repositories (e.g., with all Python packages required by the repository installed).
In previous work, setting up executable repositories is often viewed as a prerequisite for constructing training examples. This typically involves a series of complex steps such as package installation and test generation, which is still challenging for agents~\cite{swe-play} and time-consuming for human~\cite{swegym,swe-smith,R2EGym}.
Based on the observation from our analysis, we ask: \textbf{can we design a set of tasks that cover the major components for coding practice: reasoning, repo-exploration, and implementation, but do not require executable repository setup?}


% [parap-5: in this paper]
In this paper, we present \hybridmethodname, a large-scale coding agent training dataset containing a suite of coding agent training tasks that only require simple environment setup.
Based on our analysis summarized in \autoref{fig:intro}, we present a list of principles for training task design: the task needs to 
(1) match the output format of downstream tasks;
(2) include a repository exploration process; and 
(3) require non-trivial reasoning.
For scalability concerns, we further require that the task (4) must \emph{not} require a complicated environment setup.
Example tasks include function localization, issue localization, dependency search, and function generation.
As shown in \autoref{fig:intro}, even without setting up executable repositories, all our tasks cover the major intermediate components of multiple downstream tasks, and such components are achieved with a similar set of actions across tasks. 
After training on \hybridmethodname, the agent has significantly lower failure rates in reasoning, exploration, and file-editing compared to the baseline training method~\cite{swegym}.


% [para-6: experimental results]
We conduct experiments on three real-world coding agent tasks: SWE-Bench issue-solving~\citep{swebench}, SWT-Bench test generation~\citep{swt-bench}, and Commit-0 library generation~\citep{commit0}.
Without training on any of the downstream tasks, \hybridmethodname demonstrates strong task transferability on all three tasks, improving Qwen2.5Coder-32B by 25.4\% / 7.9\% / 5.1\% on SWE-Bench Verified / SWT-Bench Verified / Commit-0 Lite, which achieves comparable performance to in-domain datasets (i.e., data built for the downstream tasks). 
Additionally, we also improve the performance of training on existing in-domain datasets by combining with \hybridmethodname (e.g., we improve SWE-Play~\citep{swe-play} by 2.4\% / 4.9\% on SWE-Bench Verified / SWT-Bench Verified).


% [para-7: controlled experiment results]
To provide insights to future research on coding agent training, we conduct a series of controlled experiments to reveal what transfers and what does not for coding agents.
In addition to validating our task design principles that require output format matching, repo-exploration, and non-trivial reasoning, we observe that even successful trajectories of the same set of instances can lead to markedly different impact.
Repository diversity improves training effectiveness, but training on the same repositories used in evaluation does not inflate performance gains.
The results emphasize the importance of teacher model selection and data selection.

\section{Methodology}
\label{sec:methodology}
In this section, we first guide training task design by analyzing the commonalities shared among coding tasks and agent capabilities (\S\ref{sec:analysis-methodology}).
Based on the analysis results, we introduce a list of task design principles (\S\ref{sec:principle}) and present the four \hybridmethodname tasks that satisfy all the principles (\S\ref{sec:tasks}).
Finally, we conduct a comparison between our training tasks and real-world coding tasks (\S\ref{sec:task-verification}).

\subsection{Analysis of Coding Agent Task Transferability}
\label{sec:analysis-methodology}
With the ultimate goal of designing training tasks that transfer to diverse downstream tasks, we first investigate the commonalities shared by real-world tasks by answering:
[\textbf{RQ1}] What are the commonalities of the components (i.e., high-level problem-solving steps) to complete real-world coding tasks?
[\textbf{RQ2}] What are the commonalities of the concrete actions (i.e., commands) taken by the agents?
Since effective training must target capabilities the agent has not yet learned, we also ask
[\textbf{RQ3}] What are the abilities that the agent has not learned but are required for task completion?

\start{Analysis Setup}
Following prior works~\citep{swegym,R2EGym,swe-play}, we adopt the rejection sampling finetuning setting, where we finetune Qwen2.5-Coder-7B/32B on the successful trajectories generated for the training tasks. 
We conduct the analysis based on 200 successful trajectories sampled from each task, which are generated by Claude-4.5~\cite{claude45} using OpenHands CodeAct as the agent scaffold~\cite{openhands}


\start{Task Analysis: Decomposition of Coding Tasks}
To answer \textbf{RQ1}, we first decompose general coding agent tasks into five intermediate components: reasoning, repo-exploration, execution of existing code, solution implementation, and verification. 
We then use o3-mini~\cite{o3_mini} to categorize each agent action by the component it targets.
We manually examined 20 cases and made the same categorization as o3-mini in all the cases.

Results in \autoref{tab:action-category} show that (1) The action distribution across different components is similar for the three downstream tasks, with repo-exploration accounting for the largest share.
(2) We notice that around 70\% of the actions fall into categories that do not require setting up executable repositories: reasoning, repo-exploration, and implementation.
This is notable because executable repository setup is complicated and challenging for both humans and agents~\cite{swe-smith,swe-play} and is the bottleneck of constructing scalable training datasets.
Our analysis hence suggests a key direction: training tasks that avoid executable repository setup can also be beneficial.


\start{Task Analysis: Concrete Actions Used in Coding Tasks}
To answer \textbf{RQ2}, we analyze the concrete agent tools used in each task. 
The tools built for the OpenHands agent~\cite{openhands} include bash command execution (\texttt{execute-bash}), file viewing (\texttt{view}), and file editing (\texttt{str-replace}).
Results in \autoref{tab:action-category} show that all three tools are heavily used across downstream tasks. This suggests that \emph{the agents need to learn all the tools in training.}

For the bash execution tool, we further analyze the specific commands issued by the agent. \autoref{tab:cmd-category} shows that different tasks rely on highly similar repo-exploration commands, such as grep, find, cd, and ls, suggesting that \emph{repo-exploration skills could be broadly transferable across tasks.}


\start{Agent Capability Analysis}
To answer \textbf{RQ3}, under the setting of distillation-based training, we conduct an error analysis for the untrained student model (Qwen2.5Coder-7B, \citet{qwen25coder}), the student model trained on a baseline dataset (SWE-Gym, \citet{swegym}), and the teacher model (Claude-4.5, \citet{claude45}).
We define error categories along two axes: (1) failures in the intermediate components identified in our previous analysis, and (2) failures in the use of each tool.
We then prompt an LLM to label whether each agent trajectory exhibits these failures.


\autoref{fig:error-analysis} presents the error analysis results.
We observe several error categories where the fine-tuned model’s failure rate remains far higher than the teacher model’s: insufficient repo-exploration, insufficient reasoning, and failure/loop on the file-editing tool.
This suggests that \emph{these capabilities still have substantial room for improvement.}





\subsection{Principles for Training Task Design}
\label{sec:principle}
We summarize the analysis results in \S\ref{sec:analysis-methodology} as follows:
(1) reasoning, repo-exploration, and implementation are the dominant intermediate components shared across coding-agent tasks;
(2) The concrete types of commands to complete these components are also similar across tasks; and
(3) The performance gaps between the student and teacher models are still large for the above categories and file editing.

Based on the task commonalities and the agents' capabilities, we present the following principles for training task design:

\quad [\textbf{Principle 1}] The tasks should have the same output format as the downstream tasks.
For the downstream tasks in our evaluation, the format is generating a code patch in the codebase, which requires file editing.
A counterexample for training tasks is a variant of our issue-localization task, where we only need the agent to generate the plan to resolve the issue in the message, without making any code changes.

\quad [\textbf{Principle 2}] The tasks should involve a meaningful repository-exploration phase. 
A counterexample is a script-level code generation task (e.g., HumanEval~\cite{codex}). 
Although we can still provide a repository as context by putting the solution template file inside an empty repository, it does not involve any file localization.

\quad [\textbf{Principle 3}] The tasks should require a non-trivial level of reasoning to complete. Namely, the agent must make substantive decisions, such as choosing the problem-solving strategy, generating the precise tool call arguments, and writing the code.
A counterexample is a simple string-replacement task where we provide the exact edit location and the old/new strings. The agent can succeed by a single \texttt{str-replace} call without inspecting the codebase.


With the observation that all the major components: reasoning, exploration, and implementation, do not require an executable repository, we further require the training tasks to be scalable (i.e., easy to generate new instances):

\quad [\textbf{Principle 4}] The task setup should not require substantial effort. For instance, the task should avoid installing packages for the entire repository or generating executable test files, which are challenging for both humans and agents.

In \S\ref{sec:exp}, we will show that all \hybridmethodname tasks satisfy all four principles and generalize well to multiple downstream tasks.
In contrast, \S\ref{sec:controlled-exp} will show that all three counterexample tasks mentioned above do not yield effective task transfer.

\subsection{\hybridmethodname Tasks}
\label{sec:tasks}

In this section, we introduce four \hybridmethodname tasks that satisfy all the principles above.
% We provide the prompt for each task in Appendix \ref{app:data-construction}.

\start{Function Localization}
To boost repository exploration (principle 2), we design a task to localize a function in the entire codebase:
given a short description, the agent needs to identify the corresponding function in the codebase.
To satisfy Principle 1, which requires generating a code patch as the outcome, we require the agent to write a docstring containing the fix plan. 
We evaluate the task by checking whether a docstring is added for the correct function.
This task requires substantial reasoning (principle 3), as the agent needs to understand the code content and conduct an effective and targeted search over the entire repository, which contains 2,925 functions on average in our training set.

\start{Issue Localization}
Function localization aims to locate the code based on the description, and issue localization locates the problematic code based on an issue.
Given a GitHub issue, the task is to locate the relevant code in the repository and leave a comment containing a plan to fix the issue.
We evaluate the task by checking whether a comment is generated in the same file where the actual fix is located. 

Compared to the issue-solving task used in most prior work, constructing issue localization data does not need test execution for evaluation and can be instantiated from arbitrary GitHub issues.
However, it still requires reasoning effort on analyzing the issue, exploring the repository, planning the fix, and making successful file-editing actions.

\start{Dependency Search}
We have the third task that targets code localization, which requires file-editing, repo-exploration, and reasoning: given a function, the agent must identify all functions or classes it directly calls.
Similar to the above two tasks, we require adding comments to all these dependent modules.
To obtain the ground truth, we adopt \texttt{Jedi}, a static Python analysis tool, to resolve imported names to their defining modules.
Solving this task requires the agent to locate the target function, extract the referenced names, resolve each name to the correct module, and successfully edit the relevant files.
This is non-trivial because a codebase may contain multiple modules with the same name, and only one corresponds to the actual call.

\start{Function Generation}
Beyond the localization tasks that only aim to generate comments, we design the function generation task that requires actual code generation. 
Given a function in a codebase, we use an LLM to generate a description of its functionality.
Then we remove the function body and ask the agent to re-implement it.
To evaluate the implementation with test cases while avoiding repository installation, we adapt the RepoST~\cite{repost} method to the coding agent setting, which extracts the target function and its dependencies to a separate script and generates tests.

Here we highlight that generating \emph{executable test scripts} is substantially easier and more cost-efficient than setting up \emph{executable repositories}.
To execute the test script, we only need to install the packages needed by the extracted function and its dependencies (2.1 packages on average), while installing the entire repository requires 26.5 packages on average.
Furthermore, compared to \emph{generating a new test file} that requires understanding the repository structure and resolving relative imports, it is substantially easier to \emph{produce tests for a separate script}, which only requires seq-to-seq generation, without any agentic frameworks, making the setup process cost-efficient.

We emphasize that \hybridmethodname is not limited to the specific tasks introduced here: other task designs may also satisfy our principles.
It is also possible to construct variants of our tasks, such as localizing multiple functions, or finding the empty function before generating the function body. We leave the exploration to future works.

\subsection{Verification of \hybridmethodname Tasks}
\label{sec:task-verification}
In this section, we verify that our training tasks share commonalities with real-world tasks and remain challenging for the student models we use: Qwen2.5Coder 7B and 32B.

\start{\hybridmethodname tasks cover the majority of intermediate components in multiple real-world tasks}
As shown in \autoref{tab:action-category}, all the training tasks cover reasoning, repo-exploration, and implementation, and the function-generation task additionally includes solution verification.
We note that although our training tasks do not explicitly include executing existing code, it typically accounts for only a small fraction of an agent's trajectory.

\start{\hybridmethodname trajectories contain similar actions with real-world tasks}
As shown in \autoref{tab:cmd-category}, the training tasks use a similar set of bash commands for repo-exploration as the real-world coding tasks.
Similarly, \autoref{tab:openhands-tool-distribution} shows that the training tasks cover the full set of OpenHands tools used in downstream tasks.
Together, these results suggest that both the high-level problem-solving components and the concrete actions that achieve them can transfer across \hybridmethodname tasks and downstream tasks.


\start{\hybridmethodname tasks are still challenging for models without finetuning}
Under the setting of distillation learning, a training task is useful only if there is a performance gap between the student and teacher models
As a sanity check, before generating training data, we sample 20-30 instances from each task and evaluate the teacher model (claude-4.5-Sonnet) and student models (Qwen2.5Coder, 7B and 32B).

\autoref{tab:distillation-sanity-check} show that Claude-4.5 achieves substantially higher success rates than Qwen2.5Coder-32B on all four tasks, with gaps ranging from 23.3\% to 30.0\%. This confirms that all tasks provide sufficient room for effective distillation.

\subsection{Main Results}
\start{\hybridmethodname Shows Strong Task Transfer Performance}
Results in \autoref{tab:main} show that \hybridmethodname delivers strong task generalization performance across all three benchmarks. Relative to the base 32B model, it improves performance by 25.40 \% / 7.85 \% / 5.11 \% on the three tasks, outperforming all existing task transfer training datasets.
Notably, without training on the downstream tasks, \hybridmethodname matches or even exceeds in-domain training. For example, SWE-Play-32B reaches 31.2 \% / 16.17 \% on SWE-Bench Verified / SWT-Bench Verified, whereas \hybridmethodname-32B achieves 32.4 \% / 16.86 \%. 
This suggest that our tasks capture the commonality shared among general coding agent tasks and transfer effectively across all three downstream tasks.
These results are especially compelling because \hybridmethodname requires substantially less effort to build new training instances than prior datasets (e.g., as shown in \autoref{tab:stat}, SWE-Smith requires 128 docker images and costs 2.32\textcent per example, while \hybridmethodname is only built with 2 images and an average cost of 0.07\textcent).


\start{\hybridmethodname Improves In-Domain Training Datasets}
\autoref{tab:main} further shows that we can further improve in-domain datasets by combining with \hybridmethodname. For instance, we improve SWE-Play by 2.40\% / 4.85\% / 1.57\% on SWE-Bench Verified / SWT-Bench Verified / Commit-0 Lite.
The gains from mixing \hybridmethodname with in-domain data suggest that the two sources are complementary. \hybridmethodname primarily teaches general agent skills (e.g., reasoning, repo-exploration, and reliable tool use), while in-domain data contributes task-specific behaviors (e.g., generating tests and building libraries from scratch). Combining them both leads to additive improvements.

\start{Training on Individual Tasks}
To assess the contribution of each task, we sample 500 instances per task and train the model on each subset separately. This training size is comparable to the SWE-Gym issue-solving dataset, which contains 491 examples. As shown in \autoref{tab:single-task}, each task yields a substantial improvement over the base model, with gains ranging from 4.6\% to 11.0\%. The results suggest the advantage of constructing highly scalable training datasets.

\section{Analysis of Task Transferability}
\label{sec:controlled-exp}

We have established in \S\ref{sec:exp} that the particular tasks included in \hybridmethodname are effective for task generalization across diverse real-world coding benchmarks. 
In this section, we investigate: \textbf{what properties of these trajectories enable task transfer?}
To answer this, we run controlled ablations that systematically modify trajectory structure and measure the resulting changes in performance.

As the ablations require repeated evaluation across many variations, we keep the analyses computationally tractable by evaluating on an easier subset of SWE-bench examples (denoted as ``Easy 50''), which are solvable by Deepseek-v3, a strong reference model \cite{deepseekv3}. 


\subsection{Output Format Must Match Downstream Tasks}
While our tasks are designed around higher level tasks such as function localization and generation, we also find that \textit{how} these behaviors are expressed in the training trajectories matters. Specifically, as stated in [\textbf{Principle 1}] in \S\ref{sec:methodology}, we find that the output format of the tasks is a crucial factor.

All three downstream tasks in our experiments require the agent to generate a code patch as the output. To isolate the role of output format, we conduct a minimal ablation on our function localization task: instead of requiring the model to generate a comment in the codebase containing the fix plan, we simply ask it to generate the plan in a message.
We accordingly modify the training trajectories by removing the \texttt{str\_replace} actions for writing comments and adding the fix plan in the final message generated by the agent.

As shown in \autoref{fig:ablation}, performance on SWE-bench collapses when we remove the string replacement actions. These results suggest that for coding agent tasks, the production of \textbf{patch-like outputs} is not a superficial formatting choice but a crucial skill that the agent needs to learn. 


\subsection{Script-level Agentic Tasks Do NOT Generalize to Repo-level Tasks}
\label{sec:ablation_lcb}
We then validate [\textbf{Principle 2}], which requires the training tasks to have a repo-exploration stage. 
To test this, we implement a script-level task, LiveCodeBench (LCB) \cite{livecodebench}, which primarily evaluates function generation in a single file. 
We contrast it with two repo-level tasks: 
(1) the repo-level function generation task we use in \hybridmethodname (introduced in \S\ref{sec:methodology}), and 
(2) documentation generation, which requires the agent to generate the docstring for a given function.
For fair comparison, we wrap the coding template and test script in LCB in a dummy repository so that the model interacts with the same harness and tool API. 


\autoref{fig:ablation} shows that despite having the wrapper to make LCB superficially a repo-level task, LCB is not effective for transfer to SWE-bench. 
This negative result suggests that repository-level generalization requires more than superficial ``agentic formatting.'' 
In particular, repo-level tasks induce behaviors that are largely absent from script-level problems: identifying and navigating relevant files, grounding edits in existing codebase structure, and producing concrete patch-like modifications that apply cleanly in context.

\subsection{Task and Trajectory Complexity Matters}
\label{sec:ablation_complexity}
After identifying reasoning and planning as a crucial component in coding tasks in \S\ref{sec:methodology}, we derive [\textbf{Principle 3}] that requires the task to involve a non-trivial level of reasoning.
Here, we examine whether task generalizability improves as training supervision more closely matches the multi-step, tool-mediated interaction patterns required for coding tasks. 

We first examine tasks with ascending complexity: (1) single-shot string-replacement edits in which the task is to refactor a function by simply renaming it without replacing other usages of it, (2) documentation generation for a fixed function (as in $\S\ref{sec:ablation_lcb}$), and (3) the function localization task, which requires more complex reasoning than the previous two tasks.
We see in \autoref{fig:ablation} that as tasks become more complex and interaction-heavy, downstream SWE-bench performance improves, and models are substantially more likely to produce non-empty patches.


To isolate complexity effects from task identity, we also investigate the effect of \emph{trajectory complexity}, which is operationalized as the number of agent actions (tool calls and intermediate components) taken in successful trajectories.
We pool trajectories from our repo-level task mixture and partition them by length, selecting the shortest and longest quartiles (25\% each). 
As shown in \autoref{fig:ablation}, although the training sizes are the same, training on longer trajectories yields a large improvement in SWE-bench resolution rate, alongside a sharp reduction in empty generations. These results suggest that trajectory complexity is an important driver of task performance.



\subsection{Even Successful Trajectories of the Same Task Instances may have Different Impact}
In addition to training task design, we observe that \textbf{the teacher model also plays a crucial role in effective training}.
Specifically, we find that even successful trajectories for the same instances can yield very different distillation outcomes.
We illustrate a particular case in \autoref{fig:sampling_teacher}. 
On the issue localization task, we found that distilling from Qwen3-235B and Claude trajectories transfers well to SWE-Bench, but distilling from o3-mini trajectories degrades student performance. 
The key difference we found is that o3-mini frequently separates reasoning and actions (i.e., tool calls) into different turns.
After training on such data, the agent collapses to the distribution of thinking-only conversational turns and does not learn to call tools at all.
We edit o3-mini trajectories by simply stitching adjacent rationale and action steps into a single example. The resulting data effectively transfers to SWE-Bench, indicating that model-specific behaviors such as separating reasoning and actions can strongly influence the effectiveness of distillation.


\subsection{Sampling Strategies Affects Effectiveness}
Finally, beyond task choice and trajectory structure, we also find that how training instances are sampled impacts downstream transfer. 
We examine two key factors: 
(1) repository diversity (i.e., the number of repositories covered by the training set), which is identified by previous works~\cite{repost,swe-smith}, and 
(2) the domain of code. In the extreme case, we build training data from the exact same repositories we use in evaluation.

To investigate this, we keep the training budget fixed at 500 trajectories and sample from function localization trajectories. We compare:
(i) \emph{Min Repo-Diversity}, where we aggregate instances from a small number of large repositories (7 repositories), 
(ii) \emph{Max Repo-Diversity}, where we sample one instance per repository (500 repositories) to maximize repository coverage, and 
(iii) \emph{In-Domain Repos}, where we construct function localization trajectories based on the 12 SWE-Bench repositories.

Despite using the same number of training instances and the same SFT recipe, \emph{Max Repo-Diversity} yields higher SWE-bench resolution (\autoref{fig:sampling_teacher}). 
This suggests that exposure to a broader range of repository structures improves generalization to unseen repositories.
Surprisingly, \textbf{training on the same repositories in evaluation does not improve the performance}, suggesting that learning general agent skills is more crucial than memorizing repo-specific information.

\section{Chapter Summary}
In this chapter, we improve the task transferability of coding agents. 
We conduct in-depth analyses of the transferability across coding agent tasks.
We find that there are similar components shared by diverse real-world coding tasks (e.g., repo-exploration) that can be achieved by the agent with similar commands.
Based on the discovery, we derive a set of principles for task design, including output format matching, requiring repo-exploration, non-trivial reasoning, and simple setup.
We present four scalable and cost-efficient tasks that do not require setting up executable repositories.
With the resulting dataset, \hybridmethodname, we achieve strong task generalization results on three real-world benchmarks. For instance, even without issue-solving or test-generation data in training, we improve Qwen2.5Coder-32B by 25.4\% on SWE-Bench Verified and 7.9\% on SWT-Bench Verified.
We also improve existing in-domain datasets by combining them with \hybridmethodname (e.g., improving SWE-Play by 4.9\% on SWT-Bench Verified).

The principles introduced in this chapter focus on training task design. However, as studied in \S\ref{sec:controlled-exp}, there are other aspects that are also crucial for agent training, such as training instance selection and the concrete actions in successful training trajectories.
We thus propose \autoref{chap:effective-analysis} to investigate more training data construction principles, focusing on the effectiveness of training trajectories.






































\chapter{Discovering Effective Demonstration Behaviors for Training Coding Agents}
\label{chap:effective-analysis}

\start{Chapter Overview}
Most coding agent training methods judge the quality of demonstrations based on their final outcome, such as execution results or rubric scores.
However, we observe that the effectiveness of training also substantially depends on \emph{how} the demonstrations achieve the results.
Previous work has manually made hypotheses about which demonstration behaviors influence the performance.
To find such influential behaviors for \textbf{C}oding \textbf{A}gent \textbf{T}raining more efficiently, we present \toolName, an analysis method to automatically discover candidate behaviors by defining, extracting, and comparing the behaviors of different trained agents.
\toolName enables us to find behaviors that are influential to at least one model, including specific repo-exploration strategies, the planning and verification patterns, and the verbosity of the reasoning text.
Our insights also translate to performance gains by various methods, including data selection, agent step synthesis, and behavior-conditioned rollout.
Results show that our agent step synthesis method improves Qwen3-8B's resolved rate from 11.6\% to 17.6\% on SWE-Bench Verified.

\section{Introduction}

Agents have been trained to be effective in diverse real-world coding applications~\citep{swt-bench,commit0}.
Existing research improves coding agent post-training by constructing scalable environments~\citep{swegym,swe-smith}, designing training methods~\citep{swerl,swemaster}, and synthesizing training signals~\citep{openhands-rubric-critique,sweworld}.
Most of them still derive training signals based on the final outcome of the demonstrations, which is either obtained by execution in sandbox environments or simulated with manually-designed rubrics~\citep{openhands-rubric-critique} or LLM judges~\citep{sweworld}.

However, we observe that even when we only use successful rollouts as demonstrations in training, the exact \textbf{behaviors} reflected in the demonstrations also substantially affect the performance of the trained model. 
We conduct a preliminary study under the setting of distilling a student model from the teacher's successful rollouts.
As shown in \autoref{catradar:fig:different-teacher}, on the same set of training instances and for a fixed student model, distilling from different teachers leads to substantially different performance.
Although they all successfully solve the task, the teacher models may apply different problem-solving strategies, use different tools, and generate concrete actions with different patterns.

We thus would like to answer the question: \emph{what are the demonstration behaviors that affect coding agent training performance?}
Existing research presents manually defined rubrics on agent behaviors and empirically examines their impact on training~\citep{terminal-lego,openhands-rubric-critique,hybrid-gym}.
However, the space of coding agent behaviors is vast and open-ended, ranging from high-level problem-solving strategies to low-level tool-use patterns.
The influence of a behavior could also vary across training configurations and base models.
Manually enumerating behavioral hypotheses lacks scalability and human expertise may be limited to specific experimental settings.

In this paper, we present \toolName, an automatic analysis method to efficiently discover candidate behaviors in training demonstrations that could potentially affect \textbf{C}oding \textbf{A}gent \textbf{T}raining performance.
We leverage an LLM agent to automatically define, extract, and compare the behaviors of coding agents trained on different data sources that have different performances.
We only keep candidate behaviors that are well-defined and can distinguish the two agents we compare.
After \toolName narrows down the search space of behaviors, we examine the impact of those candidate behaviors through controlled interventions on the presence of each behavior in the training data.


We apply \toolName to 8 teacher models and 3 student models for two training tasks: R2EGym \citep{R2EGym} and Hybrid-Gym \citep{hybrid-gym}.
Guided by \toolName, we examine the impact of 10 behaviors of coding agent demonstrations and 7 of them are shown to positively affect at least one model's performance.
As shown in \autoref{catradar:fig:behavior-discovery-overview}, such influential behaviors include specific repo-exploration strategies, planning and verification patterns, and the verbosity of reasoning text.


Furthermore, we demonstrate that finding such influential behaviors can lead to actual performance gains by various methods, including data selection, agent step synthesis, and behavior-conditioned rollout.
For instance, we demonstrate that data selection based on the repo-exploration strategies we discover improves all three student models on SWE-Bench Verified~\citep{swebench} (e.g., improving the resolved rate of Qwen3-8B from 4.8\% to 11.6\%).
We also discover that simply adding 4 LLM-synthesized planning steps to each demonstration improves the resolved rates of all three student models (e.g., improving Qwen3-8B's resolved rate from 11.6\% to 17.6\%).

\section{Analysis Method: Discovering Influential Behaviors of Demonstrations}
\autoref{catradar:fig:different-teacher} shows that coding agents trained on demonstrations produced by different models can achieve different performances, but the success rates of the demonstrations cannot explain the performance gap.
We hence hypothesize that there exist a set of properties of \textbf{how} the final results are achieved that account for the performance gap, which we denote as \textbf{influential behaviors}.
Identifying such behaviors is challenging because the space of coding agent behaviors is vast, spanning from high-level problem-solving strategies to low-level implementation details.
In this section, we first present \toolName (\S\ref{catradar:sec:rubric-discovery}) to automatically narrow down the space of candidate behaviors by discovering the different behaviors of coding agents with different performances.
We then conduct controlled data intervention experiments (\S\ref{catradar:sec:controlled-exp}) to empirically examine the impact of the candidate behaviors we discovered.
We released the code of the \toolName framework and all the data intervention experiments we designed.


\subsection{\toolName: Automatic Candidate Behavior Discovery}
\label{catradar:sec:rubric-discovery}

\autoref{catradar:fig:method-overview} shows the overview of \toolName.

\start{Rollout and Discover Distinguishing Behaviors}
We run two coding agents on the same set of task instances and provide their trajectories, paired by instance, to a discovery agent (e.g., Claude-Opus-4.7).
We prompt the discovery agent to discover different \emph{behaviors} between the two agents, where each behavior is defined by a judge metric that specifies a rule for computing either a numerical or a categorical value for each trajectory.
\autoref{catradar:tab:distinct-behaviors} presents examples of behaviors and their associated judge metrics.
We only retain the behaviors with a \textbf{well-defined} judge metric that can either be computed by a deterministic script or scored by an LLM judge with high consistency.
Both are generated by the discovery agent and manually examined.
We check consistency by applying the LLM judge to the same set of examples for multiple times.

\start{Verify Distinguishability}
Given a candidate behavior and its associated judge metric, we compute the metric score for each trajectory based on its definition.
Then we treat each trajectory as one observation and fit a separate logistic regression, with agent identity (i.e., the agent that produces the trajectory) as the dependent variable and the judge metric score as the predictor, where we encode categorical values with indicator variables.
We label $N=50$ trajectories for each agent and consider the behavior to be \textbf{distinguishing} if the Wald test rejects the null hypothesis with p-value$<0.01$.

\start{Scale Up}
We add all well-defined behaviors that pass the distinguishability test to the candidate behavior list and repeat the discovery-and-verification procedure for at most $k=5$ iterations per task set and agent pair.
In each subsequent iteration, we provide the discovery agent with all existing behaviors and prompt it to identify additional differences.
We repeat this procedure across multiple training tasks and agent pairs.
We manually review and prioritize the retained behaviors for the data intervention experiments (\S\ref{catradar:sec:controlled-exp}) to examine their impact on the training performance.

\subsection{Data Intervention Methods}
\label{catradar:sec:controlled-exp}
This section aims to isolate and measure the impact of each candidate behavior discovered in \S\ref{catradar:sec:rubric-discovery} on the training performance.
We introduce two complementary intervention methods that control the presence of a target behavior while minimizing changes to other properties of the demonstrations.
For both methods, we consider a behavior to be \textbf{influential} if the presence or absence of the behavior leads to a substantial performance change.


\start{Trajectory Post-Editing}
This method adds, modifies, or removes one or more trajectory steps to control the presence of a target behavior, which can be performed by deterministic rules or an LLM.
One example is to remove the ``verify after edit'' behavior (as defined in \autoref{catradar:tab:distinct-behaviors}) from a trajectory by identifying the final file-editing action by pattern matching and removing all subsequent steps.

One major challenge is to only conduct edits that preserve \emph{trajectory consistency}: every retained step must remain supported by its preceding context.
Here we provide a non-exhaustive list of classes of edits that preserve consistency:
(1) Interchanging two sequences of steps that produce the same intermediate results that are crucial for resolving the task (e.g., two search sequences that both locate the target file);
(2) Removing steps whose outputs and state effects are not required by subsequent actions, such as unsuccessful searches whose results do not appear in subsequent actions; and
(3) Modifying steps that neither change the environment state nor provide information to subsequent actions, including steps that contained only chain-of-thought reasoning text and actions that are not executed due to wrong syntax.


\start{Behavior-Conditioned Trajectory Generation}
For behaviors that are difficult to manipulate through local edits, we generate new demonstrations for the same task instances by prompting the agent to exhibit the target behavior.
To limit differences unrelated to the target behavior, we retain an original-generated trajectory pair only if both trajectories successfully solve the task and reach the same set of essential intermediate results, which are pre-defined based on the task.
For example, in the issue-solving task, we require the original and newly generated trajectories to identify the exact same set of target files and pass all the unit tests.

\section{Analysis Results: What Behaviors Affect Coding Agent Training?}
\label{catradar:sec:analysis-results}

This section presents the analysis results of the \toolName method.
As a proof of concept, we focus on the distillation setting. 
In principle, \toolName can also be applied to other settings such as self-training or reinforcement learning.

\start{Experimental Setup}
We conduct analysis on both in-domain training: the R2E-Gym issue-solving dataset~\citep{R2EGym}, and transfer learning: the Hybrid-Gym function localization dataset~\citep{hybrid-gym}, with SWE-Bench Verified~\citep{swebench} as the evaluation dataset.
We adopt the distillation setting and apply \toolName to 8 teacher models and 3 student models, as described in \S\ref{catradar:sec:analysis-setup}.
We use the OpenHands agent harness~\citep{openhands} for all the experiments.
Since the impact of one behavior may depend on other factors such as other teacher behaviors or the student's capabilities, when we conduct data intervention experiments and compare the performance with the original data (\S\ref{catradar:sec:controlled-exp}), we experiment on multiple training tasks, teacher models, and student models (if applicable).

\subsection{\toolName Discovers Diverse Candidates}
\label{catradar:sec:distinct-behaviors}
\autoref{catradar:tab:distinct-behaviors} summarizes the candidate behaviors discovered by \toolName and examined in our experiments, along with their definitions. Compared with the behaviors that are manually hypothesized and examined in prior work, \toolName discovers a broader range of behaviors of diverse granularity, spanning trajectory-level features, problem-solving strategies, and tool-use patterns.
Our experiments show that 7 of the 10 behaviors affect student performance in at least one combination of student model, teacher model, and training dataset. Some of these findings are also consistent with prior work. For instance, Terminal-LEGO~\citep{terminal-lego} shows that verification steps in training improve performance. \toolName also discovers ``verify after edit'' as a potentially important behavior.



\subsection{Trajectory-Level Features are Not Good Indicators of Training Effectiveness}
\label{catradar:sec:traj-features}
Longer trajectories are commonly viewed as more useful training examples because they provide the model more information~\citep{swe-play}.
Under the setting of distillation, it is also a common belief that strong models often produce stronger students~\citep{swegym}. 

Our results challenge both assumptions. As shown in \autoref{catradar:fig:metric-student-correlations} and \autoref{catradar:fig:exp-len-correlation}, none of the trajectory-level features we examine is significantly correlated with student performance. 
Our hypothesis is that longer trajectories may reflect overly complicated problem-solving strategies, which may not be suitable for the student model.
Similarly, a stronger teacher model's strategies may rely on its sophisticated context understanding abilities, which are difficult to transfer to the student model, making the learned strategies less effective.

\subsection{\toolName Discovers Effective Problem-Solving Strategies}
\label{catradar:sec:repo-exploration}
Prior work shows that demonstrations should include a non-trivial repository-exploration stage and leverage an LLM judge to check whether it conducts sufficient exploration \citep{hybrid-gym}.
However, it does not specify \emph{how} the exploration is conducted.
Instead, \toolName goes a step further by identifying two concrete exploration strategies: 
\textbf{Multi-Search}, which searches for multiple keywords iteratively, and
\textbf{Target-Read}, which only reads a file after narrowing down the target to a few files.
As shown in \autoref{catradar:tab:localize-case}, the two strategies we discovered capture more fine-grained information than the high-level rubric used in prior works.


We think these two strategies are potentially useful for training for the following reasons:
by having multiple search actions in the demonstrations, the agent is trained to try different keywords if the previous ones are too broad or fail to match any files.
``Target-Read'' teaches the model not to blindly read files with low relevance, which improves the efficiency of localizing the target file.
We will show in \S\ref{catradar:sec:data-selection} and \S\ref{catradar:sec:prompt-tuning} that demonstrations containing these specific strategies improve training performance.

\subsection{Planning Steps have Different Effects on Different Models}
\toolName discovers that the planning pattern also vary across different demonstrations.
For instance, OpenHands has a ``task-tracker'' tool that creates and keeps a to-do list for the task, which is frequently used by some agents but not others.
Intuitively, the task-tracker tool assists high-level planning and plays a similar role as chain-of-thought reasoning~\citep{CoT}, which conducts explicit reasoning to guide the agent's decision-making process.

To examine whether the usage of task-tracker affects the performance, we directly remove all the task-tracker actions from the demonstrations and train the model. 
We additionally query an LLM to rewrite the text that explicitly refer to the removed steps to maintain the consistency of the trajectory.

However, results in \autoref{catradar:fig:tracker-ablation} show that having more planning steps in training does not always improve performance.
On the demonstrations generated by Claude-Opus-4.5, the presence of task-tracker steps improves the performance of Qwen2.5Coder-7B and Qwen3-8B, while degrading the performance of Qwen3-4B.
One possible explanation is that the 4B model has lower capacity and could benefit more from simpler and more straightforward demonstrations, while the larger models can better exploit complex reasoning patterns.
We will further show in \S\ref{catradar:sec:synthetic-steps} that inserting LLM-synthesized task-tracker steps improves both the 7B and 8B models.

\subsection{Verification Abilities Transfer from Simple Tasks to Complex Tasks}
\label{catradar:sec:verification}
Verification is an important stage for coding agent tasks, where the agent examines its solution after it is generated.
It can be complex for some tasks (e.g., issue-solving, where the agent needs to execute unit tests) but simple for others (e.g., function localization, where the agent only needs to read files and conduct reasoning).
\toolName discovers that the average number of verification steps varies across different teacher models.

To examine the effect of verification steps in training, we design the following data intervention experiments to control the presence of verification steps in training demonstrations:
(1) ``Remove Verify'', where we remove all the steps after the last file-editing action, and 
(2) ``Add Verify'': for demonstrations without any verification steps, we copy the verification steps from the demonstration of the same task instance generated by another agent (e.g., Claude-Opus-4.5). Other demonstrations are kept unchanged.

Surprisingly, as shown in \autoref{catradar:tab:verification-ablation}, we observe that the verification behavior transfers across different tasks.
When training the agent on function localization demonstrations with more verification steps, it also learns to perform more verification steps on the issue-solving task.

However, similar to the planning behavior, we observe that verification improves the performance of the 7B and 8B models, but does not consistently improve Qwen3-4B.
This can also be explained by the hypothesis that models with lower capacity could benefit more from simpler demonstrations.

Our results make a further step beyond the finding in Terminal-LEGO~\citep{terminal-lego}, which shows that the inspect-act-verify pattern in training trajectories improves coding agents' performance on terminal tasks.
We further show that the impact of verification also depends on other factors such as properties of the student model.

\subsection{Training on Reasoning Text Increases Trajectory Length}
\label{catradar:sec:verbosity}

\toolName discovers that the length of the text outside tool calls varies across different teacher models, which is on average 39 tokens for Claude-Opus-4.5, 98 for Qwen3-80B-NEXT, and 298 for GPT-5-mini on Hybrid-Gym.

To examine the effect of the verbosity of the reasoning text, we design an experiment that prompts an LLM to rewrite the reasoning text to reduce or increase the verbosity proportionally to its original length without adding new information. We define ``reasoning text'' as the combination of (1) the non-tool-call text and (2) the content of the ``think'' actions.
We conduct post-checking with an LLM checker to ensure the rewritten text is natural and does not add new information.
We also include a ``0x'' ablation that removes all reasoning text.

Surprisingly, \autoref{catradar:fig:verbosity} shows that increasing the verbosity of the reasoning text increases the trajectory length.
Our hypothesis is that more verbose reasoning encourages the model to articulate additional intermediate considerations, which in turn induces extra tool interactions.
Similarly, we observe in \autoref{catradar:fig:verbosity_text_only} that when we completely remove the non-tool-call text but keep the ``think'' actions, the trajectory length still substantially decreases.






\section{Practical Utility of Our Discoveries}
We apply the discoveries in \S\ref{catradar:sec:analysis-results} through three methods, ordered by increasing data-construction cost: selecting demonstrations with beneficial behaviors (\S\ref{catradar:sec:data-selection}), augmenting existing demonstrations with synthesized steps (\S\ref{catradar:sec:synthetic-steps}), and generating new demonstrations with influential behaviors (\S\ref{catradar:sec:prompt-tuning}).

\subsection{Method 1: Behavior-Aware Data Selection}
\label{catradar:sec:data-selection}

\start{Data Selection}
Given a fixed training-data budget, we select demonstrations that exhibit beneficial behaviors identified by \toolName.
Following \S\ref{catradar:sec:repo-exploration}, we retain demonstrations that exhibit both the \textbf{Multi-Search} strategy (at least three keyword searches) and \textbf{Target-Read} (narrow down to $\leq 50$ candidate files before reading).
We compare against equally sized subsets lacking either strategy: ``w/o Multi-Search'' and ``w/o Target-Read''.

\start{Results}
\autoref{catradar:tab:data-selection-strategies} shows that selecting demonstrations with both strategies consistently yields higher resolved rates than either ablation across the evaluated settings.
For example, training Qwen3-8B on 250 Claude-Opus-4.5 function-localization demonstrations with both strategies achieves 11.6\% on SWE-Bench Verified, compared with 4.8\% without Multi-Search and 5.8\% without Target-Read.
A possible explanation is that agents trained on the ``w/o Multi-Search'' ablation do not learn to recover from unsuccessful searches, and the ``w/o Target-Read'' ablation does not teach the strategy to progressively narrow down the candidate files.
One common failure case for agents trained on ``w/o Target-Read'' is to repeatedly read irrelevant files until exhausting their action budget, without a more efficient strategy to locate relevant files.

\subsection{Method 2: Adding Synthesized Agent Steps to Training Trajectories}
\label{catradar:sec:synthetic-steps}

\start{Agent Step Synthesis}
Another method is to augment existing demonstrations by inserting LLM-synthesized steps that instantiate a beneficial behavior (e.g., has high-level planning).
Particularly, we prompt an LLM to generate a task-tracker call for each function localization demonstration that specifies a to-do list: identify the target file, locate the function, generate its docstring, and verify correctness.
We insert subsequent task-tracker calls at completion points to update the corresponding items.
Implementation details are provided in \S\ref{catradar:sec:exp-implementation}.

\start{Results}
As shown in \autoref{catradar:tab:task-tracker-improvement}, adding four synthesized task-tracker actions per demonstration improves the resolved rates of Qwen2.5Coder-7B and Qwen3-8B in all evaluated settings.
For Qwen3-8B trained on Claude-Opus-4.7 demonstrations, the resolved rate increases from 11.6\% to 17.6\%.
These steps may provide explicit planning structure that helps the student organize subsequent actions.
Note that we train on the function localization task and improve issue-solving performances, suggesting that the planning behaviors transfer across tasks.


\subsection{Method 3: Behavior-Conditioned Demonstration Generation}
\label{catradar:sec:prompt-tuning}

\start{Prompt Generation}
For behaviors that are difficult to incorporate through local edits, we generate new demonstrations using a behavior-conditioned teacher prompt (\S\ref{catradar:sec:controlled-exp}).
We iteratively (1) ask an agent to write a prompt to elicit the target behaviors, (2) generate a small set of demonstrations, and (3) use an LLM judge to label their presence.
We repeat this procedure until the generated prompt significantly increases the proportion of demonstrations exhibiting the target behaviors ($p<0.05$), then use it to generate the training set.

\start{Results}
We apply this method to the two repo-exploration strategies we discovered in \S\ref{catradar:sec:repo-exploration}: Multi-Search and Target-Read.
\autoref{catradar:tab:prompt-tuning} shows that by generating demonstrations with the LLM-generated prompt, we increase the prevalence of the strategies for both the teacher and the student models.
Furthermore, training Qwen2.5Coder-7B on the resulting demonstrations significantly improves its resolved rate on SWE-Bench Verified from 6.0\% to 9.2\%.
We also observe that directly prompting the student to follow the same strategies (``prompt student'') yields a smaller gain, from 6.0\% to 7.2\%, suggesting that the student model has limited instruction-following capabilities to incorporate the strategies as prompted, and prompting the teacher model is more effective in this setting.

\section{Conclusions}
We present \toolName, an efficient analysis method, to discover potentially influential behaviors for training coding agents.
Guided by \toolName, we conduct data intervention experiments and find influential behaviors including specific repo-exploration strategies, the planning and verification patterns, and the verbosity of reasoning text.
Our insights further lead to practical improvements through data selection, agent step synthesis, and behavior-conditioned rollout, with step synthesis improving Qwen3-8B’s resolved rate from 11.6\% to 17.6\% on SWE-Bench Verified.
